## 1. Executive Summary

Step 11 transforms WorkTree X from a silent workspace into an active, cloud-orchestrated notification and reminder engine. Prior to this milestone, notifications were either local stubs or in-memory alerts without multi-device synchronization, background job scheduling, or mobile push delivery.

With Step 11, WorkTree X establishes an end-to-end event-driven notification architecture:
1. **Business Events**: Task assignments, task completion, checklist toggles, comments, and approaching due dates generate immutable notification records in `public.notifications`.
2. **Multi-Tenant RLS & User Isolation**: Notification records, user preferences, registered push devices, and scheduled reminder jobs are strictly partitioned by `organization_id` and isolated to the recipient's `auth.uid()`.
3. **Scheduled Reminders & Queue Claiming**: Implements `public.notification_jobs` with an atomic, concurrency-safe job claim mechanism using PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` inside RPC `claim_notification_jobs()`.
4. **Cloud Notification Center UI**: Real-time popover notification center in the desktop topbar and mobile drawer with live unread badge counters, instant read/unread toggling, mark-all-as-read, action deep-linking into tasks, and clean empty states.
5. **Quiet Hours & User Preferences**: Dedicated `public.notification_preferences` storing in-app, push, email toggles, timezone, and quiet hours boundaries (start/end hour) honored by the dispatch engine.
6. **OneSignal REST API & PWA Push**: Supabase Edge Function `notification-dispatch` handles server-side delivery to OneSignal REST API v16, complete with fallback handling, and client PWA Service Worker (`OneSignalSDKWorker.js`) and Web Manifest (`manifest.webmanifest`).
7. **Realtime Private Invalidation**: Integrates with Supabase Realtime via user-scoped private channels `user:<user_id>:notifications` for zero-latency live badge updates without cross-tenant leakage.

## 3. Authoritative vs Derived State Boundaries

| Layer | Authority | Storage | Mutation Strategy |
| :--- | :--- | :--- | :--- |
| **Notification Records** | Authoritative | `public.notifications` | Database trigger / RPC / Service Mutation |
| **Unread Count** | Authoritative | Server query `read_at IS NULL` | Count aggregated directly from database |
| **Device Registrations** | Authoritative | `public.push_devices` | Upserted upon OneSignal Player ID issuance |
| **User Preferences** | Authoritative | `public.notification_preferences` | Upserted by user via Settings modal |
| **Delivery Jobs** | Authoritative | `public.notification_jobs` | Generated by triggers; claimed by Edge Function |
| **UI Notification List** | Derived / Cache | Memory (`state.notifications`) | Refetched on Realtime event or pull |
| **Badge Counter** | Derived | DOM `#notificationDot` / counter | Computed from authoritative server state |

## 5. Job Queue & Atomic Claim Mechanism

To prevent race conditions, double dispatch, or deadlock when multiple Edge Function runners execute concurrently, the queue uses the PostgreSQL `FOR UPDATE SKIP LOCKED` pattern:

```sql
CREATE OR REPLACE FUNCTION public.claim_notification_jobs(
  p_worker_id TEXT,
  p_batch_size INT DEFAULT 10,
  p_lock_timeout_seconds INT DEFAULT 60
)
RETURNS SETOF public.notification_jobs
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  RETURN QUERY
  WITH claimable AS (
    SELECT id
    FROM public.notification_jobs
    WHERE status = 'pending'
      AND scheduled_for <= now()
      AND (locked_at IS NULL OR locked_at < now() - (p_lock_timeout_seconds || ' seconds')::interval)
      AND attempt_count < max_attempts
    ORDER BY scheduled_for ASC
    LIMIT p_batch_size
    FOR UPDATE SKIP LOCKED
  )
  UPDATE public.notification_jobs j
  SET
    status = 'processing',
    locked_at = now(),
    locked_by = p_worker_id,
    attempt_count = j.attempt_count + 1,
    updated_at = now()
  FROM claimable
  WHERE j.id = claimable.id
  RETURNING j.*;
END;
$$;
```

## 6. Realtime Private Notification Channels

In conformance with `AGENTS.md` and Step 10 Realtime requirements:
- Notification events do NOT broadcast raw payload over public channels.
- Private channel naming: `user:<user_uuid>:notifications`.
- Authorization policy on `realtime.messages` ensures a client can ONLY listen to their own user channel:
  ```sql
  CREATE POLICY "Users can listen to their own notifications channel"
  ON realtime.messages FOR SELECT TO authenticated
  USING (
    realtime.topic() = 'user:' || auth.uid()::text || ':notifications'
  );
  ```
- Broadcast events (`new_notification`, `unread_count_updated`) inform the client to perform a canonical refetch of `NotificationService.getUnreadCount()` and `getRecentNotifications()`.

## 7. Edge Function Implementation (`notification-dispatch`)

Location: `supabase/functions/notification-dispatch/index.ts`
Key Responsibilities:
1. Claims pending notification jobs using `claim_notification_jobs(workerId, 25)`.
2. Inspects recipient's `notification_preferences` for:
   - Push enabled state.
   - Quiet hours evaluation in the recipient's timezone.
3. Retrieves active `push_devices` for recipient (`player_id` from OneSignal).
4. Dispatches push request to OneSignal REST API v16:
   - Endpoint: `https://onesignal.com/api/v1/notifications`
   - Headers: `Authorization: Key <ONESIGNAL_REST_API_KEY>`, `Content-Type: application/json`
   - Target: `include_player_ids: [playerIds]`
   - Payload: Title, Body, App Icon, URL deep-link to task/view.
5. On success: marks job as `completed`.
6. On error: increments attempt, records `last_error`, backs off, or marks `failed` if `attempt_count >= max_attempts`.
7. Broadcasts invalidation signal to Supabase Realtime channel `user:<recipient_id>:notifications`.
